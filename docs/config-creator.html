Getting Started

Choose a starting template or start from scratch. Every field has a sensible default.

This page is both a reference guide and a config builder. Every setting has an expandable ℹ What does this do? panel explaining the runtime behavior. Browse the sections to learn what each feature does, then download a ready-to-use app_config.json when you're done. Use ⌘S to save at any time.

Datum Proxy

Via Datum proxy (Posit Connect deployment).

Read-only child tab with state & presets disabled.

ℹ When should I use each template?
  • Blank — start with all defaults enabled. Good for learning or customising from scratch.
  • Direct PostgreSQL — connect directly via SQLAlchemy. Best for local dev, VPN access, or environments where the app can reach the DB directly.
  • Datum Proxy — routes through the Datum REST proxy. Required on Posit Connect where direct DB connections are blocked by network policy.
  • Sub-Table / Detail Tab — preconfigured for child/detail views: read-only, no state persistence, no presets, filters locked. Designed for zero-DB-call tab spinup when combined with shared_cache_key.

The working table the app reads from and writes to. All cell edits, approvals, and rejections modify rows directly in this table. Format: schema.table_name (e.g., public.my_data).

Modifications table: Every cell edit, approval, and rejection is logged here with the column name, old value, new value, username, and timestamp. Powers the Undo feature and provides a full audit trail. The table is auto-created on first use.

If the column doesn't exist in the table, it's added automatically. Leave blank to disable status tracking entirely.

Table & Columns

Configure the table display, primary key, column visibility, and column name masks.

How columns work: By default the app shows all columns from the data table. Use Default Visible Columns to limit what users see on load (they can still toggle others via the column picker). Editable Columns and Read-Only Columns control which cells are editable.
One or more columns that uniquely identify each row. Press Enter to add.
ℹ What does this do?
The primary key uniquely identifies each row and is used for:
  • Edit tracking — the modifications log records which row was changed by PK.
  • Undo — locates the exact row to revert.
  • Approval — identifies which rows to mark as Approved/Rejected.
  • Row selection — drives checkbox selection and Review Detail events.
If auto_detect_pk is ON (Database section), the app reads the PK from the PostgreSQL table metadata. Set it here to override or when auto-detection isn't available.
Columns shown by default. Leave empty to show all. Press Enter to add.
Leave empty to allow editing all columns (except readonly).
These columns cannot be edited regardless of editable_columns.
ℹ How do editable / read-only interact?
Priority order:
  1. readonly_columns always wins — these cells are never editable.
  2. If editable_columns is non-empty, only those columns are editable (minus readonly).
  3. If editable_columns is empty, all columns are editable (minus readonly).
The primary key column(s) and the status column are automatically treated as read-only.

Filters & Search

Configure search, filters, and default filter values applied on load.

Filtering architecture: Filters can be applied from the column header dropdowns, the sidebar facets, or pre-set via default_filters. When fix_filter is ON, users see only the pre-configured filters and cannot change them — ideal for sub-table / detail-tab views.
ℹ What does this do?
Shows a search bar above the table. Typing filters rows in real-time across all searchable columns (case-insensitive substring match). In lazy-loading mode, search is executed as a SQL ILIKE query.
Leave empty to search all text columns.
Shown as sidebar checkbox+count panels for quick filtering.
ℹ What does this do?
Each facet column gets a sidebar panel showing every unique value with a count and checkbox. Uncheck a value to hide those rows. Counts update dynamically as other filters are applied. Great for categorical columns like Department, Region, or Category.
When on, users can only use the default_filters — they cannot add or remove filters.
ℹ What does this do?
ON: The filter row on the table is locked. Users see the data pre-filtered by default_filters but cannot add, edit, or remove any filter. Ideal for sub-table / detail-tab deployments where the parent app controls what data is shown.
OFF (default): Users can freely add column filters via the header dropdown.

State & Cache

Controls whether sort, filter, and page state persists across sessions, and the cross-session data cache.

Sub-table best practice: For detail-tab / sub-table deployments, set persist_state = false and presets_enabled = false to eliminate all state-related DB calls. Combine with shared_cache_key to go fully zero-DB after the initial load.
When off, skips all state DB calls. Use false for sub-table / detail-tab mode.
ℹ What does this do?
ON: When a user sorts, filters, changes page, or rearranges columns, their UI state is saved to the state_table. Next time they open the app, everything is restored to where they left off. Each sub-flag below controls which parts persist.

OFF: No state DB calls at all. Every session starts with default sort/filter/page. This is the correct setting for sub-table or detail-tab views where the parent app controls the view. Also eliminates the DNS/DB overhead that would otherwise occur on every tab spinup.

Shared Data Cache

When set, all browser sessions share one in-memory copy of the data. Only the first session hits the DB; subsequent sessions get the cached copy.

A unique string identifier. All instances with the same key share the cache.
ℹ What does this do?
Enables the shared in-memory data cache. All app instances (browser sessions) using the same key share a single copy of the data in server memory.
  • First session loads data from the DB and populates the cache.
  • Subsequent sessions get a copy from the cache — zero DB calls for data loading.
  • The cache is thread-safe (guarded by a lock) and TTL-based.
Combine with persist_state = false and presets_enabled = false for a fully zero-DB startup on sub-table/detail tabs. The key should be unique per logical dataset (e.g., "my_project_detail_v1").
How long (seconds) the cached data lives before the next session re-fetches. Default: 300 (5 min).
ℹ What does this do?
After TTL seconds, the cache entry expires. The next session to start will re-fetch from the DB and refresh the cache. Sessions already running are unaffected — they keep their in-memory copy.

Tip: Set a longer TTL (e.g., 3600 = 1 hour) for data that rarely changes. Set 0 for always-fresh data (every first session per process restart hits the DB).

Feature Flags

Toggle major features on or off. Click ℹ What does this do? on any flag to see its runtime behavior.

Approve/reject buttons, status column tracking.
ℹ What does this do?
Adds Approve ✓ and Reject ✗ buttons to the toolbar.
  • Select one or more rows, then click Approve or Reject.
  • The status_column (default: Status) is updated to the configured status_values.approved / status_values.rejected value.
  • Approved rows show a green badge; rejected rows show red.
  • If approval_assignment is configured, approving a row also copies values from source columns to target columns (e.g., copy Draft_Value → Final_Value).
  • Every approval/rejection is logged in the mods_table with the username and timestamp.
When OFF: No approval buttons appear. The status column is not managed by the app.
ℹ What does this do?
Shows a Save button in the toolbar that commits pending cell edits to the database.
  • Cell edits are staged in-memory until Save is clicked.
  • On save, each modified cell is written to the data_table and a corresponding record is inserted into the mods_table with the old value, new value, username, and timestamp.
  • The row's status_column is set to "Edited" (if approval workflow is enabled).
When OFF: Edits are auto-committed on cell blur (when you click away from the cell). There is no batch-save step.
ℹ What does this do?
Shows an Export CSV ↓ button in the toolbar.
  • Downloads the current view as a CSV file — respects active filters, search query, sort order, and column selection.
  • Only the columns currently visible in the table are included.
  • The filename includes the table title and current date.
When OFF: No export button. Users cannot download data from the UI.
ℹ What does this do?
Shows an Undo ↺ button in the toolbar.
  • Reverts the last cell edit — restores the original value in the data_table.
  • The corresponding modification record in the mods_table is marked as undone.
  • If the undo restores a cell to its very first value, the row's status reverts to its previous state.
  • Only the most recent edit can be undone (single-level undo).
When OFF: No undo capability. Edits are permanent once committed.
ℹ What does this do?
Adds a 📋 copy icon to each column header.
  • Click the icon to copy all visible (filtered) values in that column to your clipboard.
  • Values are newline-separated — paste directly into Excel, Google Sheets, or any text editor.
  • Respects current filters and search: only the rows currently displayed are copied.
  • A toast notification confirms the copy with the number of values.
When OFF: Column headers show only the column name — no copy icon.
Status distribution histogram and filter in sidebar.
ℹ What does this do?
Shows a status distribution panel in the left sidebar.
  • Displays a count and percentage bar for each status value (Unprocessed, Edited, Approved, Rejected).
  • Each status has a checkbox — uncheck to hide rows with that status.

Long-running SQL transform with cached materialised view.
ℹ What does this do?
Adds a Synthesis button that runs a user-defined SQL query against the database.
  • The SQL result is materialised into a PostgreSQL table (named by result_table_prefix).
  • The result is cached for ttl_minutes — subsequent clicks serve the cached result if still fresh.
  • Opens a modal showing the result as a downloadable table.
  • Useful for cross-table aggregations, pivot summaries, or computed reports derived from the current data.

Emits a review_detail event via the commute layer with selected row PKs.
ℹ What does this do?
Adds a Review Detail button to the toolbar (label is customizable).
  • Select one or more rows, then click the button.
  • Emits a review_detail event through the commute layer containing the primary key(s) of selected rows.
  • The commute layer enables cross-app communication — a parent app or sibling tab can listen for this event and display a detail view.
  • In multi-select mode, all selected row PKs are included. Otherwise, only the first selected row.
When OFF: No Review Detail button. No commute events are emitted from row selection.

Synthesis

Configure the SQL transform feature. Enable it first on the Feature Flags page.

How synthesis works: When a user clicks the Synthesis button, the configured SQL query runs against the database. The result is materialised into a temporary table and displayed in a modal. The result is cached for ttl_minutes — subsequent clicks serve the cached result until it expires.
The SQL transform to run. Result is materialised into a PostgreSQL table.
ℹ Query tips
  • The query runs with the same database connection as the main app.
  • You can reference the data_table and any other tables in the same schema.
  • The result is materialised (CREATE TABLE AS) — it must return rows and columns.
  • Use this for cross-table joins, aggregations, or pivot summaries.
0 = always regenerate.

Permissions

Role-based access control. Editors can modify data; viewers are read-only.

How permissions work: When a user opens the app, their Posit Connect username is checked against the user_roles map. If found, they get that role. Otherwise, they get the default_role. Viewers can see all data, sort, filter, and export, but cannot edit cells, approve, reject, or undo. Editors have full access.
Applied when the user is not listed in the user roles table below.
ℹ What does this do?
viewer: Safe default — new/unknown users can browse but not modify data. Recommended for production.
editor: All users can edit by default. Only use this for small teams where everyone is trusted.

For sub-table / detail-tab deployments, set to viewer to ensure the detail view is strictly read-only.

Approval Assignment

▶
Column-to-column copy on approval. When a row is approved, source column value is written to target column.
ℹ What does this do?
Automates a common workflow: when a row is approved, copy the value from one column to another.

Example: Map Draft_Name → Final_Name. When a reviewer clicks Approve, the draft value is automatically copied to the final column. Multiple mappings are supported — all run atomically on each approval.

Review Detail

Configure the Review Detail button that emits events via the commute layer.

Commute layer: The commute system enables cross-app communication on Posit Connect. When Review Detail is clicked, the app emits an event with the selected row's primary key(s). A parent app or sibling tab can listen for this event and open a detail view, navigate to a record, or trigger a workflow.
When on, the event includes all selected rows. When off, only the first selected row.
ℹ What does this do?
OFF (single): The commute event payload contains the PK of the first selected row only. Clicking with multiple rows selected sends only the topmost.
ON (multi): The event includes an array of all selected row PKs. The receiving app can process them in batch (e.g., open a comparison view or bulk detail report).
